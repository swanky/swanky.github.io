# ketchup：補進度＋列出待決定的事

改編自 pstack `ketchup`（catch up 的諧音）。假設站主記得自己上一則訊息，之後的事一概不知道；通知和 subagent 的回報不算他的訊息。

## 收集（這一輪只讀，不改任何東西）

- 自己從那則訊息之後做的事、subagent 的回報、其他人在對話裡的訊息。
- 每個碰過的 commit、push、部署、背景工作的**目前狀態**：實際查，不憑記憶。
- 每個要寫出來的數字，對照來源再確認一次；有更正就說出來。

**待決定事項**＝只有站主能做的決定或動作：對外文案方向、價格、push 上線、刪資料、花錢（含 codex 額度）、你沒有的權限。自己還能做的工作不是待決定事項。不要為了湊數編一個出來。

每個事項收集：它會對訪客或站主造成什麼改變、支持你建議的證據、風險、你的建議。不知道的寫「不確定」。

## 寫回覆

字數花在決定上，不花在過程。

1. **第一句**：說有幾件事在等他，或說沒有。
2. **發生了什麼**：100 字以內，每件他要求的事一行，寫成說得出口的句子：「文章已上線，手機版排版正常」，不寫「文章：完成」。說清楚是完成、還在跑、失敗，還是沒驗證。順路發現並修掉的問題也點名。沒改變什麼的過程不寫。
3. **待決定事項**：每件約 30 字，風險高的排前面：
   - 要他做的決定（合併、核准、選哪個）＋你的建議。
   - 它會改變什麼、證據、風險（風險低也要寫，例如「低風險：只改顏色」）。
   - 有先後順序或不可逆的，寫進建議裡。
   - 多選一時，每個選項寫它換來什麼、代價是什麼。
4. 最後一行：你還能自己繼續做的工作。

用語照 `docs/brand-book.md` §3：白話、不用工程術語。不寫 commit hash、檔案路徑、指令、測試數字，除非站主要用它來行動（例如要他打開的檔案，給完整 `C:\` 路徑）。

## 圖

有比文字更好懂的才放：改版前後截圖、選項並排、流程怎麼運作的 Mermaid 圖。不要畫狀態清單或待辦清單；Markdown 表格不算圖。同一件事不要在文字和圖裡講兩次。

## Verification

回覆裡每個待決定事項都有建議與風險；每個「完成」都有本輪實際查過的狀態支撐，沒查到的寫「未驗證」。
