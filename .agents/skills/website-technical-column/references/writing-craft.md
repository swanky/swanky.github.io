# 寫作手藝：句子層級的修稿準則

本檔補 `docs/brand-book.md` §3（白話、判斷先行、不說太滿、禁用詞）沒有涵蓋的句子與段落層級。改編自 cursor/plugins 的 `pstack/skills/technical-writing`（Diátaxis、Google developer style、STE、Global English），只留中文用得上的部分。brand-book 與 `AGENTS.md` 的硬規則優先。

用法：初稿寫完、進第 8 步驗證前，照本檔從頭修一輪。

## 三條總則

- **刪掉沒有作用的字。** 拿掉後句子意思不變，那個字就刪。「進行判斷」是「判斷」，「基於這些結果」是「根據結果」，「值得注意的是」直接刪。
- **用日常短詞。** 「用」不寫「使用／利用」，「幫」不寫「協助／賦能」，「做」不寫「執行／進行」。長詞要換來更精準才值得。
- **規則讓句子變差時，換個寫法或保持原樣。** 每條都守、讀起來卻像機器寫的，就是失敗。

## 先決定文體（一篇只用一種）

| 讀者要的是 | 文體 | 骨架 |
|---|---|---|
| 看懂一件事為什麼重要、怎麼運作 | 觀念文（多數專欄） | SKILL.md 第 4 步的 9 段骨架；可以有立場 |
| 照著做完一件事（裝工具、設定流程） | 操作文 | 目標 → 前提 → 編號步驟（每步寫出「這時你會看到…」）→ 出錯時怎麼辦 |
| 查數字、參數、比較 | 查詢資料 | 表格為主，只描述、不說服；放文末或獨立段落 |

不要混：觀念文裡塞一長串安裝步驟，或操作文中途開始辯論取捨。拆開，互相連結。操作文的標題寫成任務：「把 Claude Code 接上 GitHub」，不寫「GitHub 整合」。

## 節奏與具體

- **長短句交錯。** 短句落下判斷，長句帶著條件或後果。整篇都是短句，或整篇都是長句，都像機器寫的。
- **一句一個意思，不等於每句一樣長。** 兩個意思的長句拆開；一個意思的長句可以留。
- **寫具體，不寫空泛。** 不寫「schema 變動可能帶來問題」，寫「欄位改名讓 build 失敗」。不寫「效能大幅提升」，寫數字和條件。
- **觀念文要有立場。** 列完優缺點後，寫出你怎麼看（brand-book §3.1-4）。查詢資料保持中性。

## 中文 AI 腔：看到就改

| 不要寫 | 改法 |
|---|---|
| 值得注意的是、更值得注意的是、需要指出的是 | 刪掉，直接說那件事；真的重要就放段首 |
| 總而言之、綜上所述、總的來說 | 刪掉；結論本身就是結論 |
| 在當今…的時代、隨著…的快速發展 | 刪掉，從具體場景開始 |
| 不僅…更…、不只是…而是… 連用 | 一篇最多一次；多半直接說後半句 |
| 賦能、深入探討、全方位、無縫、助力、打造、新範式 | 換成具體動作：「讓…能…」「拆開看」「接上」 |
| 進行＋動詞（進行判斷、進行部署） | 只留動詞 |
| 這是一個…的設計（替前文下總評） | 直接寫它防止了什麼、換來什麼 |
| 這意味著… 開頭的句子連續出現 | 換成「所以」，或直接寫後果 |

連續兩句不要用同一個詞開頭。

## 指涉與命名

- **「這／它／此」要指得清楚。** 有疑慮就重複名詞。不要用「這」指前面一整句話。
- **一樣東西只用一個名字。** 前面叫「排程」，後面就不要改叫「定期任務」「循環」。三個名字，讀者會以為是三樣東西。
- **程式碼、指令、檔名照實寫。** 用 `reference_max_tokens`、`/loop`，不要換成「長度參數」「迴圈指令」之類的代稱；第一次出現時用白話補一句它做什麼。
- **不自創黑話。** 用工程師說出口的詞：「移動」「刪除」「只會往下調的預算」。真的需要一個名詞，第一次出現就說清楚它是什麼。

## 操作步驟與標題

- 條件寫在動作前面：「要刪除排程，執行 `/loop stop`。」
- 一步一個動作；先寫常見情況，例外放後面。
- 步驟裡不寫「只要」「很簡單」「輕鬆」：讀者會在這裡，就是因為不簡單。
- **標題寫出重點，不只寫主題。** 「先決定文體」優於「文體」；TOC 的每一行讀下來，應該就是全文摘要。
- 順序用編號清單，其他用項目符號；清單前用完整句子帶出，各項句型一致。

## 修改前／修改後

站上真實段落（`_posts/2026-03-21-claude-code-terminal-magic-guide.md`）：

> 結果會直接出現在對話上下文裡，Claude 可以基於這些結果進行判斷和後續操作，而不只是單純輸出狀態文字。值得注意的是，定期任務在建立三天後會自動到期——這是一個防止遺忘循環無限運行的設計。

修改後（事實不增不減）：

> 結果會直接回到對話裡，Claude 能接著判斷下一步，不只是印出一行狀態。定期任務建立三天後會自動到期，所以忘了關的排程，不會一直跑下去。

改了什麼：刪「基於這些結果進行」「值得注意的是」「這是一個…的設計」；「上下文」換成白話；後果直接寫成「不會一直跑下去」。

標題反例（同站 `_posts/2026-03-21-claude-code-design-system.md`）：「數位產品開發的新範式：AI 賦能的設計無感轉型」。四個抽象詞疊在一起，讀者讀完還是不知道這節要說什麼。改寫時寫出這節的結論。
