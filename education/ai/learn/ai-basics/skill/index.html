先從一個煩惱開始

同樣的三條規矩，每次都要重講一遍

史旺姬常請 AI 幫忙約會議。每一次，她都要重新交代同樣的三件事：避開午休、會議標題照指定格式、寄出前先給她看。這次說完，下次換一件事、換一位同事，又要從頭說一遍。

先想一想

你有沒有哪件事，每週都要重新交代一次？不是工作內容每次一模一樣，而是基本流程和注意事項一直重複。

這一幕要回答

既然重複，能不能把做法寫一次，整理成一本用得上就翻開的手冊，讓其他人也能沿用？這本寫給 AI 的手冊，就叫 Skill。

只記一句每次不一樣的寫在交辦裡；一直重複的做法，值得寫成一本手冊。

關鍵詞 4：Skill

Skill：寫給 AI 的「新人工作手冊」

Skill 可以先用一句話理解：寫給 AI 的標準作業流程。它通常是一個資料夾，裡面有一份 SKILL.md，寫下這類工作應該怎麼做，也可以放範本或其他附件。

寫一次，每次照做：史旺姬把約會議的規矩，寫成一支叫 schedule-meeting 的 Skill（示意）。

schedule-meeting 手冊裡寫什麼（示意規則）
  1. 避開 12:00～13:30 的午休時間
  2. 沒特別說，會議預設一小時
  3. 會議標題照指定格式
  4. 發出邀請前，先給使用者確認

下次只要提出這一次的需求——找哪幾個人、談什麼主題——AI 讀到這本手冊，就有一套可以照著走的方法。懂流程的人寫一次，其他人也能共用，不用每個人重新摸索。

常見誤會
訓練

寫 Skill 不是在訓練 AI

模型的參數沒有因為你寫了一份手冊而改變。做法是需要時把手冊內容交給它，讓它照著做；拿掉手冊，它就不會。

Anthropic 也公開了一批範例手冊，例如處理 PDF、Excel、Word、簡報檔的 Skill，以及幫你建立 Skill 的 skill-creator（後面「怎麼叫出 Skill」會再看到）。手冊不只能用在排會議：它的價值，是把你原本就會的工作方法，變成別人和 AI 都讀得懂、能重複使用的說明。

只記一句Skill 讓 AI 從「聰明的新人」，變成「懂你們做法的同事」。

出處：Anthropic〈Agent Skills〉（2025-10-16 發布，2025-12-18 更新）；Anthropic 公開範例 Skill：github.com/anthropics/skills（2026-10-06 查閱）。schedule-meeting 與其規則為本教材虛構示意。

實物長這樣（示意）

一份 SKILL.md 的長相：寫給 AI 的 SOP（標準作業流程）

換史旺姬的第二支示意 Skill：meeting-notes，把會議逐字稿整理成紀錄；上面的 schedule-meeting 格式完全相同。看起來像程式碼，先別緊張——這其實是一份有結構的工作說明，對照四個標號一段一段看。

1名稱（name）

這支 Skill 叫什麼，用英文小寫和連字號。最上面兩條 --- 夾住的是「封面資料」：名稱＋說明。

2說明（description）

最重要的一段：AI 靠這段判斷「什麼時候該用我」。要寫清楚用途，和使用者會講的關鍵字。

3步驟與規則

就是 SOP 本體：照順序做什麼、遇到例外怎麼辦。像「沒提到期限就寫待確認、不要猜」這種規則，正是讓成果符合你做法的關鍵。

4範本與附件

範本、參考資料、小程式，放在同一個資料夾，需要時才讀。

  • 這種寫法叫 Markdown（.md）。用 # 當標題、- 當條列的純文字寫法，記事本就能寫、就能打開，不用會寫程式。
  • 如果這份只能記一個地方，記 ② 說明。正文再完整，也要先讓 AI 在對的時機想到打開它。下一段就說為什麼。

只記一句會寫 SOP，就會寫 Skill。

示意：meeting-notes 為本教材虛構的示意 Skill；SKILL.md 格式依 Claude Code Docs〈Extend Claude with skills〉。

Skill 最聰明的設計

手冊一層一層翻（正式名稱：漸進式揭露）

AI 不是一開始就把每一本手冊全文讀完。名字聽起來抽象，其實就是：不要一開始把所有內容全部攤出來，需要到哪一層，再讀到哪一層。就像先看手冊目錄，再翻到用得上的那一章。

第 1 層：先放目錄

每支 Skill 的名稱和說明，像手冊目錄上的一行：這本是排會議、那本是整理會議紀錄。「約 100 Token」只是說目錄很精簡，不是固定配額。

第 2 層：用得上才翻開

AI 判斷這一次用得上，才打開那份 SKILL.md 全文，讀完整的步驟和規則。不是每次一進來就先把幾十本手冊讀完。

第 3 層：需要才拿附件

做到一半需要範本或參考資料，再去拿。如果附的是小程式，通常是執行後把結果交回來，不必把整份程式碼當成閱讀材料。

如果所有手冊一開始全文上桌

佔掉大半張桌子，重要的內容反而更難被注意到。還記得 {% include ai-learn/chref.html module=mod slug="llm" anchor="context" label="第二幕的辦公桌" %}嗎？桌面就這麼大。

只放目錄，用到才翻

桌面留給這次真正要用的內容。也因為這樣，目錄上那一行（description）寫不清楚用途和使用情境，AI 可能根本想不到該翻這本。

只記一句桌子有限，只先放目錄；「說明」寫不清楚，AI 就不會想到翻開。

出處：Claude Docs〈Agent Skills overview〉；Anthropic Engineering〈Equipping agents for the real world with Agent Skills〉；Claude Code Docs〈Extend Claude with skills〉。schedule-meeting、meeting-notes 為示意 Skill，pdf、xlsx 為 Anthropic 官方 Skill。

Prompt、Skill、MCP 一張表分清楚

這三個詞最容易混在一起，所以不要各講一套例子，全部用「排會議」來看。

Prompt 說「做什麼」

這一次的對象、時間和目標。缺了它，AI 不知道你這次要什麼。

Skill 教「怎麼做」

避開午休、標題格式、發出前先確認。換了會議主題，這些做法照樣沿用。

MCP 讓 AI「做得到」

透過行事曆的工具，AI 才能真的查到空檔、把邀請送進系統。沒有工具，說得再清楚也不能憑空操作。

分分看

下面這些，屬於 Prompt、Skill，還是 MCP？

「幫我約小芳，週五對一下報價」

這是這一次的交辦：約誰、什麼時候、談什麼，每次都不一樣。

「沒提到期限，就寫『待確認』，不要猜」

這是 meeting-notes 手冊裡的規則：每次整理紀錄都適用，寫一次就好。

讓 AI 能查到三個人的行事曆空檔

這是「做得到」的能力，要靠行事曆的工具接上系統。

「會議預設一小時，避開午休」

每次約會議都一樣的做法，正是 schedule-meeting 手冊的內容。

只記一句Prompt 說做什麼，Skill 教怎麼做，MCP 讓 AI 做得到。

出處：Claude Docs〈Agent Skills overview〉；Claude Code Docs〈Connect Claude Code to tools via MCP〉（tool search）。schedule-meeting 與行事曆 Server 為示意。

每次開工都會先讀一遍的固定規矩，不管這次做什麼事都適用。

Skill＝特定工作的手冊

遇到那一類工作才翻開。平常只在目錄上佔一行。

「寫」手冊：記事本就可以

選題指南

第一支 Skill，挑哪件工作？

會叫用之後，先別急著做很多支。第一支 Skill，挑常做、花時間、步驟講得出來的工作；每次都不一樣、要人際判斷，或碰到個資、法律責任的，先不要。

怎麼替候選工作打分數、排出第一個題目，第六幕有完整做法：{% include ai-learn/chref.html module=mod slug="agent" anchor="pick" label="選題三問與打分示範" %}。

分分看

這些工作，適合拿來寫第一支 Skill 嗎？

整理每週會議紀錄

每週都做、步驟講得出來（摘要、決議、待辦表），就是 meeting-notes 那種手冊。

面談回饋

每次情況都不同，又要人際判斷，規則很難寫清楚。

彙整週報給主管

頻率固定、格式固定，很適合寫成手冊。

含個資名單的整理

就算很花時間，也不要因此跳過資料安全和責任問題。

只記一句先挑常做、花時間、步驟講得出來的工作；要人際判斷或碰到個資的，先不要。

小測驗 7／10：寫好的 Skill 為什麼沒被用到？

史旺姬寫了第三支 Skill「整理週報」（weekly-report），步驟寫得很完整。她對 AI 說「幫我整理這週的週報」，AI 卻沒用這支 Skill。最可能的原因是？

因為漸進式揭露，AI 平常只看得到每支 Skill 的名稱和說明，靠說明判斷要不要打開全文。說明沒寫到使用者會講的字，步驟寫得再好也不會被打開。
  • A 步驟太長：AI 決定要不要打開之前，根本還沒讀到步驟，步驟長短不會影響它選不選。
  • B 沒接 MCP：Skill 是工作說明，不一定要配 MCP 工具；整理你貼上的內容，不用接工具。
  • D 先讀完全文：正好相反，開工時只放名稱和說明，不會先讀全文。
看答案
C，說明（description）是手冊的入口：沒寫到「整理週報」這類字，AI 就想不到要打開它。

先把「手冊內容好不好」和「AI 有沒有想到打開這本手冊」分成兩件事，再選答案。答錯的話，回到上面的「手冊一層一層翻」重看。

Skill 沒被用上？

說明（description）是入口：先讓 AI 想得到它

AI 真的打開手冊本來就該用這本手冊的需求

觸發率

在本來應該用到某支 Skill 的需求裡，AI 有多少次真的想到要打開它。就像新人遇到該翻手冊的狀況時，有沒有想到去翻。觸發率低，問題通常不在手冊內容，而在目錄上那一行。

說明太短：AI 對不上

使用者說「幫我整理這週的週報」，說明裡卻沒有任何一個對得上的字。

name: weekly-report description: 週報。

寫清楚用途＋使用者會講的字

照 meeting-notes 的寫法：先說它做什麼，再說什麼情況該用。

name: weekly-report description: 把這週的工作紀錄整理成給主管看的 週報。使用者提到「週報」「整理這週的進度」 時使用。

兩段 description 都是示意寫法。

  1. 寫清楚這支 Skill 做什麼（用途）。
  2. 寫進使用者實際會講的字（什麼時候用）。
  3. 用的時候追問「用了哪支 Skill」，再對照成果確認。

只記一句手冊正文要寫好，目錄上的那一行也要寫清楚。

出處：Claude Docs〈Agent Skills overview〉；Claude Code Docs〈Extend Claude with skills〉。weekly-report 為本教材虛構的示意 Skill。
